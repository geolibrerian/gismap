Project package (.gisx) for derived or local data

Can an AI agent hand me a GISMap Online project when the map uses data it derived itself, like call counts joined to neighborhoods?

Yes, from a running GISMap Online page. Links only reference public URLs, so derived data travels in a .gisx project package: the agent loads the file into GISMap Online, styles it, calls gisMapOnline.project.exportPackage() to get the package GISMap Online itself writes, checks the archive, reimports it into a fresh page and returns that exact file. A ZIP the agent assembled by hand is not a project package.

Machine-readable recipeAll recipes

Ask for it like this

  • “Join these two years of 311 calls to neighborhoods and give me the GISMap Online project”
  • “Send me this map as a .gisx file”
  • “Package the derived layer so I can open it in GISMap Online”

Inputs

Accepts: Derived GeoJSON, Local spatial file (GeoJSON, shapefile ZIP, KML, CSV, GeoPackage), Public layers mixed with local ones. Engines: maplibre, arcgis.

  • data: The local or derived file, written by the agent from real queried values.
  • title: The project name; it becomes the .gisx file name.

Optional:

  • style: Renderer, palette and 3D settings applied in the app.
  • description: Method and caveats, such as excluded records or what an extrusion height means.

Steps

Discover → inspect → plan → validate → execute → verify → share. Each step names where it runs; none is a hosted REST endpoint.

  1. discover: Read llms.txt, this recipe and api/capabilities.json; note the engine and execution environment you actually have. (Declarative URL; https://gismap.online/llms.txt, https://gismap.online/api/capabilities.json, https://gismap.online/api/manifest.json)
  2. inspect: Read the source metadata: geometry type, field names and types, spatial reference, extent, sentinels and query support. Query real values before filtering; never invent fields. (Declarative URL, Standalone JavaScript, In-browser API; <layer URL>?f=pjson, sources.inspect, sources.detectSentinels, layers.metadata)
  3. plan: Derive the data from real queries (for counts per area, use server-side statistics or a spatial join you can report) and keep the totals: features, records without an area, nulls. Decide the style before opening the page. (Standalone JavaScript; sources.inspect, queries)
  4. execute: Open GISMap Online, close the welcome card, add the file through Add data (local file input or drop). Wait for the layer to report loaded and ready with the expected feature count, apply the style, and set the project name. (In-browser API; layers.list, layers.metadata, describe)
  5. verify: Read back the style (layers.list / mapSpec.fromCurrent) before exporting: color field, palette, height field and mode are the ones requested. (In-browser API; layers.list, mapSpec.fromCurrent)
  6. execute: Call await gisMapOnline.project.exportPackage(); it returns { fileName, mimeType, blob } without a download dialog. Write the blob to disk yourself. If you use the Project > Download > Project package (.gisx) menu instead, capture the real download path through the browser's download mechanism; do not search the disk and guess. (In-browser API; project.exportPackage)
  7. verify: List the archive: it must hold project.json, README.txt and each local layer's file at its projectPath. Then import that exact file into a fresh GISMap Online page (Project > Import project file) and confirm the title, layer count, feature count, Ready state, fields and style. (In-browser API; layers.list, describe)
  8. share: Attach the verified .gisx and report its path, size, contents and the reimport result. Say that no share link exists for local data unless the user publishes it as a public layer. (In-browser API; project.exportPackage)

Result

A ZIP written by GISMap Online with the .gisx extension: project.json (the project snapshot), README.txt and the local layer files.

  • Project package (.gisx) · In-browser API. Opens with Project > Import project file; carries local data.
  • Labeled data fallback (.zip) · Outside GISMap Online · static. Only when the export fails, named as a data package, never as .gisx.

Verify before reporting success

  • Layer loaded and ready with the expected feature count before export
  • Style read back from the page before export
  • File came from project.exportPackage or a captured GISMap Online download
  • Archive lists project.json and the layer file
  • Reimported into a fresh page: title, layers, features, fields, style and 3D settings intact

Report prepared, validated, loaded, rendered and verified separately, and partial or failed when they apply. A generated link alone is only prepared.

Limitations

  • Needs a running GISMap Online page; there is no hosted export.
  • Local and derived data cannot go into a share link, QR or embed.
  • The package holds a snapshot of the data, not a live query.

If something goes wrong

  • If the export or capture fails, say so and name the failed step. Do not rename a ZIP to .gisx or call it a project package.
  • Offer the derived data as a clearly labeled fallback, for example <name>_data_package.zip.
  • If the reimport drops styling, report which settings were lost.

Examples

Example · prepared · checked 2026-10-21

311 call increase by neighborhood, 2022 to 2023

Prompt: “Use the FY2022 and FY2023 311 call layers and the neighborhood polygons. Count calls per neighborhood each year, compute increase and percent change, color by increase on a red-blue diverging ramp, extrude by increase × 0.2, and send me the .gisx project.”

Data: City 311 calls FY2022 and FY2023, and neighborhood polygons (ArcGIS Online)

Open the result

What was checked:

  • The link opens only the public neighborhood polygons; the derived counts and styling exist only in the .gisx.
  • Written from an agent run that delivered a hand-made ZIP instead of the .gisx; the expected result is 129 neighborhood polygons with calls_2022, calls_2023, increase and pct_change.
  • Calls with no neighborhood value were excluded from the totals and must be reported.
