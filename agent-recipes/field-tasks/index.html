Location-based field tasks

Can an AI agent create a field inspection checklist for a place that someone can open on their phone?

Yes, without code. A chatbot writes https://gismap.online/?workflow=tasks#fieldTask=json:<URI-encoded JSON> with the title, location, coordinates, notes and up to ten steps. The person in the field checks in, ticks off steps and sends back a report link. No account or server is involved.

Machine-readable recipeAll recipes

Ask for it like this

  • “Make a field inspection checklist for this park”
  • “Create five tasks to do on site at this address”
  • “Send someone to check these locations”

Inputs

Accepts: Address or coordinates, Features of a public layer (by object ID). Engines: maplibre, arcgis.

  • location: Verified coordinates or an address.
  • title: Task package title.
  • tasks: The things to do; five per package by default.

Optional:

  • instructions: Notes for the person (up to 500 characters).
  • features: Up to five features to visit, by layer URL and object ID.

Steps

Discover → inspect → plan → validate → execute → verify → share. Each step names where it runs; none is a hosted REST endpoint.

  1. discover: Read llms.txt, this recipe and api/capabilities.json; note the engine and execution environment you actually have. (Declarative URL; https://gismap.online/llms.txt, https://gismap.online/api/capabilities.json, https://gismap.online/api/manifest.json)
  2. inspect: Resolve the location to coordinates (or pick features by object ID from a real layer). (Outside GISMap, Standalone JavaScript; https://nominatim.openstreetmap.org/, <layer URL>/query)
  3. plan: Write the task: id, title, location, latitude, longitude, notes, steps [{ text }], optional features [{ layerUrl, objectId, latitude, longitude, label }]. Requests for more than five tasks become several packages ('… 1 of 2') with the same id prefix; never drop one. (Standalone JavaScript; field-task-share.js#serializeFieldTask, field-task-share.js#FIELD_TASK_LIMITS)
  4. execute: Without code: write https://gismap.online/?workflow=tasks#fieldTask=json:<encodeURIComponent(JSON)> with { title, location, lat, lon, notes, steps: ["…"], features: [{ layerUrl, objectId, lat, lon, label }] }. With code: createFieldTaskUrl from "https://gismap.online/js/field-task-share.js" for a compact, QR-safe link. (Declarative URL, Standalone JavaScript; #fieldTask=json:<payload>, field-task-share.js#createFieldTaskUrl, field-task-share.js#readableFieldTaskPayload)
  5. verify: Decode the link (decodeFieldTask) and compare title, location and every step; with a browser, open it and confirm the task panel, map location and check-in button. (Standalone JavaScript, In-browser API; field-task-share.js#decodeFieldTask, describe)
  6. share: Return the assignment link (QR-safe). The completed report comes back as a separate link made by the person in the field. (Declarative URL; ?workflow=tasks#fieldTask=<payload>)

Result

One task package: title, location, coordinates, notes, steps (checklist), features to visit; returned reports add check-in, steps done, notes, who and when.

  • Assignment link (#fieldTask=) · Standalone JavaScript
  • QR code · Outside GISMap · static. Links are kept under 2,800 characters; the app's Share dialog draws one.
  • Completion report link · Declarative URL. Created by the field worker in the app, never by the agent.

Verify before reporting success

  • Correct location on the map
  • All requested tasks present, five per package
  • Steps, title and notes decode unchanged
  • Mobile task panel opens with check-in and steps

Report prepared, validated, loaded, rendered and verified separately, and partial or failed when they apply. A generated link alone is only prepared.

Limitations

  • Each task is a checklist step: steps have text only, not separate IDs, evidence types or completion rules.
  • Photos stay on the field device and go into the PDF report; links never carry them. A check-in records place and time, not proof that the work was done.
  • Up to 10 steps, 5 features and 500 characters of notes per package; progress persists only in the report link the worker sends back.

If something goes wrong

  • If the link is too long, shorten notes and step text or split the package.
  • Never fabricate a check-in, photo or completed report.
